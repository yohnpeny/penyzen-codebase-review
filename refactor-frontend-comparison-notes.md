## Executive Summary & Architectural Vision

As the author of the frontend refactor (`yohnpeny/refactor-frontend`), my primary goal was to prepare Penyzen for rapid scale. A crowdfunding platform is not a static MVP or basic CRUD dashboard; as campaigns gain momentum, transaction volumes surge, and new features roll out (Stripe Connect payouts, Chariot DAF donations, identity verification tiers, donor transparency ledgers, and team collaboration), a monolithic codebase quickly becomes unmaintainable.

To ensure long-term developer velocity and platform stability, I introduced:
1. **Clean Architecture + Domain-Driven Design (DDD):** Isolating domains (campaigns, pledges, donors, organizations, auth) into self-contained slices with explicit boundaries.
2. **MVVM (Model-View-ViewModel):** Decoupling presentation components from data access and business logic.
3. **Server State Management (TanStack Query):** Eliminating manual `useState`/`useEffect` data fetching, stale-data bugs, and race conditions with centralized caching and background invalidation.
4. **Declarative Validation (React Hook Form + Zod v4):** Providing accessible, real-time form validation aligned with modern resolvers.
5. **Modern Tech Baseline:** Upgrading to Next.js 15 (resolving Next 14 CVEs) and Tailwind CSS v4 (instant `@tailwindcss/postcss` compilation with CSS variables).
6. **Component & Regression Testing:** Introducing Vitest and React Testing Library to protect UI components against visual and functional regressions.

### My Pragmatic Approach to Merging
While my architecture was designed with feature releases and large-scale applications in mind, I completely recognize that certain aspects of the refactor must be balanced against immediate production needs:
* **Live Revenue First:** We must protect critical money flows (e.g., Stripe direct charges in `dev`) during the merge.
* **Full-Stack Zod v4 Upgrade:** Because React Hook Form requires tight alignment with Zod via `@hookform/resolvers`, and because our platform is currently in active development, **now is the ideal window to upgrade all backend microservices to Zod v4**, rather than accumulating technical debt that will be significantly more painful to migrate once we are live in production.
* **Public Discovery & SEO:** Public campaign pages must combine server-side rendering (SSR/ISR) for search engines and social link previews with TanStack Query's rich client-side interactivity.

## Action Plan & Next Steps

### Phase 1: High-Priority Merge Fixes
1. **Full-Stack Zod v4 Alignment:** Bump `services/*/package.json` to Zod 4 and resolve any schema differences across the monorepo now while in active development.
2. **Session Expiry Preservation:** In `apps/web/src/lib/api/client.ts`, retain `${window.location.pathname}${window.location.search}` and the `'session-expired'` reason notice.
3. **Amplify Build Script:** Add `npm run build --workspace=@penyzen/shared` to `amplify.yml`.
4. **Temporary Payment Isolation:** Retain `dev`'s single donation panel file to ensure uninterrupted live Stripe direct charge processing.

### Phase 2: SEO & Public Discoverability
1. **Home Page ISR:** Add `export const revalidate = 60;` to `apps/web/src/app/page.tsx` with resilient error fallbacks.
2. **Browse Page SSR:** Prefetch/load initial campaign list on the server in `CampaignsPage` and pass to `CampaignsBrowser`.
3. **Image Domains:** Explicitly whitelist production S3 and CloudFront hosts in `next.config.mjs`.

### Phase 3: Post-Merge Modernization Follow-ups
1. **Payment Architecture Refactor:** Port `dev`'s Stripe direct charge logic into the modular 9-file donation architecture backed by automated end-to-end tests.
2. **Form Constraint Synchronization:** Align client Zod schemas with Cognito and backend user service constraints.
3. **Dead Code Pruning:** Remove unused `zustand` and orphaned UI primitives.
